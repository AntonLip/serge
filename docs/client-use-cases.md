# Use case: клиентский портал

Формальные use case роли **Клиент** и смежных действий сотрудников по выдаче доступа и обработке клиентских заявок.

Остальные UC сотрудников — `staff-use-cases.md`. Диаграммы — `diagrams.md`.

Общие соглашения:

| Элемент | Значение |
|---|---|
| Система | CleanDistrict (ООО «Чистый округ») |
| Роль Client | доступ только к `/Portal` и своим заявкам |
| Аутентификация | `/Account/Login`, пароль выдаётся сотрудником |
| Источник заявки | `RequestSource.Client` |
| Валюта / время | RUB (российский рубль); желаемый срок вводится локально (Europe/Minsk), хранится в UTC |

---

## UC-C01. Выдать доступ клиенту

| Поле | Описание |
|---|---|
| **ID** | UC-C01 |
| **Название** | Выдать доступ представителю организации |
| **Актёр** | Администратор, Менеджер |
| **Заинтересованные лица** | Представитель клиента |
| **Предусловия** | Актёр авторизован; организация активна в справочнике клиентов |
| **Триггер** | Актёр выбирает «Выдать доступ» в разделе «Доступ клиентов» |
| **Основной поток** | 1. Система показывает форму: организация, ФИО, email, пароль.<br>2. Актёр заполняет поля и подтверждает.<br>3. Система проверяет активность организации и корректность данных.<br>4. Система создаёт пользователя Identity с `ClientId`, ролью `Client`, подтверждённым email.<br>5. Система показывает список доступов клиентов. |
| **Альтернативы** | **A1.** Организация не выбрана / неактивна → ошибка валидации, форма остаётся.<br>**A2.** Email уже занят или пароль не соответствует политике Identity → ошибки в форме, пользователь не создаётся. |
| **Постусловия** | Учётная запись клиента существует и может войти в портал |
| **Интерфейс** | `/ClientUsers/Create` |

## UC-C02. Войти в клиентский портал

| Поле | Описание |
|---|---|
| **ID** | UC-C02 |
| **Название** | Аутентификация клиента |
| **Актёр** | Клиент |
| **Предусловия** | Учётная запись создана (UC-C01) и не заблокирована |
| **Триггер** | Клиент открывает страницу входа |
| **Основной поток** | 1. Клиент вводит email и пароль.<br>2. Система проверяет учётные данные.<br>3. При успехе открывается интерфейс роли Client с пунктом «Мои заявки». |
| **Альтернативы** | **A1.** Неверные данные → сообщение об ошибке.<br>**A2.** Учётная запись заблокирована → вход запрещён. |
| **Постусловия** | Установлена сессия пользователя с ролью Client |
| **Интерфейс** | `/Account/Login` |

## UC-C03. Просмотреть список заявок организации

| Поле | Описание |
|---|---|
| **ID** | UC-C03 |
| **Название** | Просмотр заявок организации |
| **Актёр** | Клиент |
| **Предусловия** | UC-C02 выполнен; у пользователя задан `ClientId` |
| **Триггер** | Клиент открывает «Мои заявки» |
| **Основной поток** | 1. Система определяет организацию клиента.<br>2. Система выбирает заявки, у которых объект принадлежит этой организации.<br>3. Система показывает таблицу: номер, объект, дата создания, желаемый срок, стоимость, статус. |
| **Альтернативы** | **A1.** Заявок нет → пустое состояние с предложением создать заявку.<br>**A2.** `ClientId` отсутствует → отказ в доступе (403). |
| **Постусловия** | Данные только просмотрены |
| **Интерфейс** | `/Portal` |

## UC-C04. Создать заявку

| Поле | Описание |
|---|---|
| **ID** | UC-C04 |
| **Название** | Создание клиентской заявки |
| **Актёр** | Клиент |
| **Предусловия** | UC-C02; у организации есть хотя бы один активный объект |
| **Триггер** | Клиент выбирает «Создать заявку» |
| **Основной поток** | 1. Система показывает форму и список активных объектов организации клиента.<br>2. Клиент указывает объект, нужную услугу, описание, желаемый срок, контактное лицо и телефон.<br>3. Система проверяет, что объект принадлежит организации клиента и активен.<br>4. Система создаёт заявку: статус **Новая**, источник **От клиента**, тариф и стоимость пустые, приоритет обычный, фиксируются автор и контакты.<br>5. Система добавляет запись в историю статусов («Заявка отправлена клиентом»).<br>6. Система уведомляет диспетчерскую доску (SignalR).<br>7. Клиент перенаправляется на карточку созданной заявки. |
| **Альтернативы** | **A1.** Ошибки валидации полей → форма с сообщениями.<br>**A2.** Выбран чужой/неактивный объект → ошибка по полю «Объект». |
| **Постусловия** | Заявка сохранена и доступна сотрудникам в `/Requests` |
| **Интерфейс** | `/Portal/Create` |

### Бизнес-правила UC-C04

- Клиент **не** выбирает тариф и **не** задаёт стоимость.
- Номер заявки формируется как `З-{год}/{порядковый номер}`.
- Желаемый срок конвертируется из локального времени в UTC.

## UC-C05. Просмотреть карточку заявки

| Поле | Описание |
|---|---|
| **ID** | UC-C05 |
| **Название** | Просмотр деталей заявки |
| **Актёр** | Клиент |
| **Предусловия** | UC-C02; заявка относится к объекту организации клиента |
| **Триггер** | Клиент открывает номер заявки в списке |
| **Основной поток** | 1. Система проверяет принадлежность заявки организации клиента.<br>2. Система показывает объект, запрошенную услугу, назначенный тариф (если есть), описание, срок, стоимость, контакт, историю статусов. |
| **Альтернативы** | **A1.** Заявка другой организации или не найдена → 404.<br>**A2.** Статус **Новая** и источник клиентский → дополнительно доступна форма отмены (UC-C06). |
| **Постусловия** | Данные только просмотрены |
| **Интерфейс** | `/Portal/Details/{id}` |

## UC-C06. Отменить новую заявку

| Поле | Описание |
|---|---|
| **ID** | UC-C06 |
| **Название** | Отмена новой клиентской заявки |
| **Актёр** | Клиент |
| **Предусловия** | Заявка создана клиентом (`Source = Client`) и имеет статус **Новая** |
| **Триггер** | Клиент отправляет форму отмены на карточке заявки |
| **Основной поток** | 1. Клиент указывает причину отмены.<br>2. Система проверяет статус и источник.<br>3. Система переводит заявку в **Отменена**, пишет историю, уведомляет SignalR.<br>4. Клиент видит обновлённую карточку. |
| **Альтернативы** | **A1.** Причина пустая → ошибка, статус не меняется.<br>**A2.** Заявка уже не **Новая** или не клиентская → отказ с сообщением; отмена возможна только через сотрудника. |
| **Постусловия** | Заявка в статусе **Отменена**; повторное открытие невозможно |
| **Интерфейс** | `POST /Portal/Cancel` |

## UC-C07. Назначить тариф и согласовать клиентскую заявку

| Поле | Описание |
|---|---|
| **ID** | UC-C07 |
| **Название** | Обработка клиентской заявки сотрудником |
| **Актёр** | Администратор, Менеджер, Диспетчер |
| **Заинтересованные лица** | Клиент |
| **Предусловия** | Существует заявка с источником **От клиента** и статусом **Новая** |
| **Триггер** | Сотрудник открывает карточку заявки в «Заявки» и заполняет блок согласования |
| **Основной поток** | 1. Система показывает выбор активного тарифа и поле согласованной стоимости.<br>2. Актёр выбирает тариф, указывает стоимость в рублях и подтверждает.<br>3. Система сохраняет `TariffId` и `EstimatedCost`, переводит заявку в **Согласована**.<br>4. Система пишет историю и уведомляет диспетчерскую доску. |
| **Альтернативы** | **A1.** Попытка согласовать без тарифа/стоимости обычным «Согласовать» → отказ: нужна обработка через `ProcessClient`.<br>**A2.** Заявка уже обработана → сообщение об ошибке.<br>**A3.** Неактивный тариф или некорректная стоимость → ошибка. |
| **Постусловия** | Заявка согласована и готова к созданию наряда |
| **Интерфейс** | `POST /Requests/ProcessClient` |

## UC-C08. Заблокировать / разблокировать доступ клиента

| Поле | Описание |
|---|---|
| **ID** | UC-C08 |
| **Название** | Управление блокировкой клиентского доступа |
| **Актёр** | Администратор, Менеджер |
| **Предусловия** | Существует пользователь с ролью Client и заполненным `ClientId` |
| **Триггер** | Актёр нажимает блокировку / разблокировку в списке доступов |
| **Основной поток** | 1. Система переключает `LockoutEnd`.<br>2. При блокировке клиент не может выполнить UC-C02.<br>3. При разблокировке вход снова разрешён. |
| **Альтернативы** | **A1.** Пользователь не клиентский → операция отклоняется. |
| **Постусловия** | Состояние блокировки обновлено |
| **Интерфейс** | `POST /ClientUsers/ToggleLockout` |

## Вне области клиентских use case

Клиент **не** выполняет:

- регистрацию самостоятельно;
- создание/редактирование объектов, договоров, тарифов;
- создание нарядов и назначение ресурсов;
- загрузку отчётов бригады;
- работу с автопарком и аналитикой сотрудников.

После UC-C07 жизненный цикл заявки продолжается общими правилами статусов (наряд → работы → закрытие), описанными в `domain-rules.md`.
