# Описание прецедентов системы «Чистый округ»

Для удобства рассмотрения прецеденты сгруппированы в блоки по предметным сущностям и операциям. В отличие от типичного CRUD-приложения с физическим удалением записей, в системе для справочников применяется деактивация, для заявок — отмена со сменой статуса, для договоров — закрытие или истечение срока. При ошибках валидации форма возвращается пользователю с сообщениями; при исключениях отображается страница ошибки. Изменяющие операции выполняются методом POST с проверкой antiforgery-токена; права доступа проверяются на сервере по ролям ASP.NET Identity.

---

## Блок 1. Управление сущностью «Клиент» и связанными объектами

Одноимённый прецедент просмотра означает получение списка клиентов. Для отображения списка администратору или менеджеру необходимо нажать пункт меню **«Клиенты»**, после чего формируется запрос к базе данных PostgreSQL на выборку клиентов (с учётом строки поиска по наименованию или контактному лицу). Список преобразуется к модели представления и размещается на генерируемой HTML-странице. Руководитель имеет доступ к просмотру без возможности изменения.

Следующим прецедентом блока является добавление клиента. Для добавления необходимо нажать кнопку **«Добавить клиента»** на странице списка. Пользователю отображается форма (наименование, контактное лицо, телефон, email, адрес). После заполнения и подтверждения кнопкой **«Сохранить»** модель представления преобразуется в сущность предметной области и сохраняется через Entity Framework Core. При успешном добавлении пользователь перенаправляется на карточку или список клиентов. При ошибках заполнения форма отображается повторно с указанием некорректных полей.

Прецедент изменения клиента выполняется со страницы карточки клиента кнопкой **«Редактировать»**. Загружается форма с текущими значениями; после подтверждения выполняется UPDATE в базе данных, пользователь возвращается к карточке. Для прекращения использования клиента без потери истории предусмотрен прецедент деактивации: система устанавливает признак неактивности, физическое удаление не выполняется.

Отдельно в блоке рассматриваются объекты обслуживания, логически подчинённые клиенту. Прецедент добавления объекта запускается кнопкой **«Добавить объект»** в карточке клиента. Форма содержит название, адрес, площадь в м², персонального менеджера и примечания. После сохранения объект связывается с клиентом и может участвовать в договорах, расчётах и заявках. Изменение объекта выполняется кнопкой **«Изменить»** в строке объекта; деактивация объекта исключает его из выбора при создании новых клиентских заявок, сохраняя исторические связи.

## Блок 2. Управление сущностью «Договор»

Прецедент получения списка договоров инициируется пунктом меню **«Договоры»**. Система формирует запрос к базе с фильтрами по номеру/клиенту и статусу, преобразует результат к модели представления и выводит HTML-таблицу.

Добавление договора выполняется кнопкой создания на странице списка. Пользователь указывает уникальный номер, клиента, период действия, статус, сумму в рублях и перечень услуг. Дополнительно допускается загрузка скана договора (PDF, JPG или PNG размером до 10 МБ): файл сохраняется во внутреннем файловом хранилище вне публичного каталога сайта, а в записи договора фиксируется путь к файлу. После успешного сохранения пользователь перенаправляется к списку или карточке договора. Дата окончания не может предшествовать дате начала; при нарушении правила модель не сохраняется.

Изменение договора выполняется кнопкой редактирования: форма загружается с текущими значениями, при необходимости загружается новый файл взамен прежнего. Печатная форма договора открывается отдельным прецедентом просмотра HTML-страницы, пригодной для сохранения в PDF средствами браузера. Скачивание вложения образует отдельный прецедент выдачи файла из хранилища с проверкой прав доступа.

## Блок 3. Управление сущностью «Расчёт стоимости»

Прецедент списка расчётов вызывается пунктом **«Расчёты»**. Система выбирает сохранённые расчёты с подключением объекта, клиента и тарифа, преобразует их к представлению и отображает на HTML-странице.

Добавление расчёта выполняется менеджером или администратором. На форме указываются объект, тариф, площадь, часы работы бригады, машино-часы, дополнительные материалы и признак срочности. Модель представления передаётся в прикладной сервис расчёта: последовательно вычисляются базовая цена, составляющие по площади и ставкам, материалы, при необходимости коэффициент срочности, затем НДС по ставке тарифа и итог в рублях. Результат сохраняется как снимок (позиции, параметры, ставка НДС, суммы). Последующее изменение тарифа не пересчитывает уже сохранённые документы. После успешного сохранения пользователь перенаправляется к карточке расчёта. Доступны прецеденты просмотра деталей и печатной формы. Руководитель использует только прецеденты просмотра.

---

## Блок 4. Управление сущностью «Заявка» (сотрудник)

Одноимённый прецедент списка заявок открывается пунктом **«Заявки»**. Система выполняет запрос с фильтрами по статусу, приоритету, источнику (сотрудник или клиент), объекту и признаку просрочки. Список преобразуется к модели представления и выводится на HTML-странице; диспетчерская доска дополнительно получает уведомления через SignalR при изменениях.

Добавление заявки сотрудником (менеджер, диспетчер, администратор) выполняется кнопкой создания. Форма включает объект, тариф, описание, приоритет и желаемый срок; опционально подставляются данные из существующего расчёта. После подтверждения модель преобразуется в сущность заявки с источником «От сотрудника», статусом «Новая», фиксируются автор и метка времени (UTC). Формируется запись истории статусов. Пользователь перенаправляется на карточку заявки.

Для согласования новой заявки сотрудника предусмотрен прецедент смены статуса: на карточке нажимается **«Согласовать заявку»**, статус становится «Согласована», история дополняется. Закрытие выполненной заявки и отмена (для статусов «Новая», «Согласована», «Назначена») оформляются аналогичными POST-прецедентами смены статуса; при отмене обязательна причина. Отмена назначенной заявки сопровождается отменой связанного наряда и освобождением техники при отсутствии других активных назначений. Закрытую или отменённую заявку повторно открыть нельзя.

Изменение «как у тура» (редактирование всех полей в любой момент) для заявки не предусмотрено: жизненный цикл управляется переходами статусов по правилам предметной области. Просмотр карточки заявки выводит объект, клиента, менеджера, тариф, стоимость, контакты, историю и доступные по роли действия.

---

## Блок 5. Клиентские заявки и портал

Отдельным подблоком рассматриваются прецеденты роли «Клиент». Публичная саморегистрация отсутствует. Прецедент выдачи доступа выполняется администратором или менеджером в разделе **«Доступ клиентов»**: выбирается организация, указываются ФИО, email и пароль. Система создаёт пользователя Identity с привязкой к клиенту и ролью Client. Блокировка и разблокировка доступа образуют парный прецедент через установку срока блокировки учётной записи.

После входа клиент работает в разделе **«Мои заявки»**. Прецедент списка выбирает только заявки по объектам организации клиента. Добавление заявки: кнопка **«Создать заявку»**, форма с объектом своей организации, текстовым описанием нужной услуги, описанием работ, желаемым сроком и контактами. Тариф и стоимость клиент не задаёт. После сохранения заявка получает источник «От клиента» и статус «Новая»; диспетчерская доска уведомляется через SignalR.

Обработка такой заявки сотрудником — отдельный прецедент: на карточке в разделе заявок сотрудник выбирает тариф, указывает согласованную стоимость и нажимает **«Назначить и согласовать»**. Статус становится «Согласована». Прямое согласование без тарифа и стоимости для клиентской новой заявки запрещено.

Пока заявка в статусе «Новая», клиент может выполнить прецедент отмены с указанием причины. После согласования отмена доступна только сотруднику.

---

## Блок 6. Управление сущностью «Наряд»

Прецедент списка нарядов открывается пунктом **«Наряды»**. Бригадир фактически работает с нарядами своей бригады; остальные сотрудники с правом Staff видят операционный список в рамках роли.

Добавление наряда доступно диспетчеру и администратору только для согласованной заявки без существующего наряда. На форме указываются бригада, плановый интервал и при необходимости несколько единиц техники. Система проверяет: конец интервала позже начала; отсутствие пересечений по бригаде, машине и водителю; доступность техники; наличие закреплённого водителя у выбранной машины. После успешного преобразования модели создаётся наряд, заявка переходит в «Назначена», техника — в статус «Назначена». Пользователь перенаправляется на карточку наряда. Ручные работы допускаются без техники.

Прецедент начала работ: бригадир (или администратор) нажимает действие начала на карточке наряда; наряд и связанная заявка переходят «В работе».

Прецедент завершения: открывается форма отчёта (фактический объём, трудозатраты, стоимость материалов, комментарий). Допускается до пяти фотографий JPG/PNG до 5 МБ; файлы сохраняются в защищённом хранилище, в отчёте фиксируются пути. После успешного сохранения наряд и заявка получают статус «Выполнена», техника освобождается при отсутствии других активных назначений. Доступны прецеденты печати наряда и просмотра фотографий отчёта.

---

## Блок 7. Управление сущностью «Техника» (автопарк)

Прецедент списка техники вызывается пунктом **«Автопарк»** с фильтром по статусу. Карточка показывает параметры машины, водителя, историю ТО и ремонтов. Просмотр доступен механику, администратору, диспетчеру и руководителю; изменение — механику и администратору.

Добавление техники: форма с названием, государственным номером, типом, пробегом, моточасами, водителем и плановыми показателями ТО. После сохранения запись появляется в списке. Изменение выполняется кнопкой редактирования на карточке. Списание образует прецедент перевода в статус «Списана» при отсутствии активного наряда; списанную технику нельзя назначить на новый наряд.

Подблок технического обслуживания: создание записи ТО с плановой датой; старт ТО переводит машину в «На ТО» (запрещено при активном наряде); завершение фиксирует стоимость и примечания, по умолчанию планирует следующее ТО через 90 дней / +10 000 км / +500 моточасов, возвращает машину в «Доступна», если параллельно не идёт ремонт.

Подблок ремонта: регистрация ремонта с описанием переводит машину в «В ремонте»; завершение с указанием стоимости и запчастей возвращает доступность при отсутствии ТО. В отчёты по затратам автопарка попадают только завершённые ТО и ремонты.

## Блок 8. Справочники администратора: тарифы, бригады, сотрудники

Аналогичные группы прецедентов разработаны для сущностей «Тариф», «Бригада» и «Сотрудник». Они доступны из раздела **«Справочники»** роли администратора.

Для тарифов: список, добавление (наименование, тип услуги, единица, ставки, коэффициент срочности, ставка НДС), изменение и переключение активности. Деактивированный тариф не выбирается в новых расчётах и заявках, но сохраняется в уже созданных документах.

Для бригад: список с составом, добавление (название, специализация), изменение и деактивация. Сотрудник может входить не более чем в одну бригаду.

Для сотрудников: список, добавление (ФИО, должность, телефон, бригада), изменение и деактивация. Отличительной особенностью преобразования моделей является проверка уникальности привязки к бригаде и использование справочника при назначении менеджера объекта и водителя техники.

---

## Блок 9. Управление сущностью «Пользователь»

Прецедент списка пользователей сотрудников открывается пунктом **«Пользователи»** (администратор). Отображаются учётные записи без клиентской привязки. Добавление пользователя: ФИО, email, пароль, роль (администратор, менеджер, диспетчер, бригадир, механик, руководитель). Система создаёт запись ASP.NET Identity, хеширует пароль и назначает роль. Блокировка и разблокировка выполняются переключением срока блокировки.

Учётные записи клиентов ведутся отдельным блоком «Доступ клиентов» (см. блок 5) и не смешиваются со staff-пользователями в одном списке.

---

## Блок 10. Прецеденты Login / Logout

Прецеденты входа и выхода обеспечивают аутентификацию. Для входа неавторизованный пользователь открывает страницу входа (или перенаправляется на неё при обращении к защищённому ресурсу), заполняет email и пароль и подтверждает отправку формы. Система находит пользователя по нормализованному имени/email, проверяет хеш пароля средствами Identity. При совпадении выдаётся аутентификационная cookie с заявлениями о ролях; сотрудник попадает на рабочую панель, клиент — в портал заявок. При неверных данных форма отображается с ошибкой; при блокировке вход запрещён.

Для выхода пользователь нажимает **«Выйти»**: cookie сессии удаляются, разрешения прекращаются, отображается страница входа.

Рабочая панель после входа сотрудника образует отдельный прецедент агрегированного просмотра: система выполняет набор запросов (новые и просроченные заявки, активные наряды, доступная техника, ближайшие ТО, истекающие договоры, последние заявки) и формирует HTML-сводку.

---

## Блок 11. Получение отчётов

Отдельным сценарием является прецедент получения отчётов. Для отображения сводки следует выбрать пункт меню **«Отчёты»**. Система запрашивает агрегированные показатели: общее число заявок, выполненные, доля выполненных в срок, затраты автопарка. Далее доступны детальные отчёты: заявки за выбранный период, работы по объектам, загрузка бригад и техники, затраты на ТО и ремонты. Данные преобразуются к табличным моделям представления и выводятся на HTML-страницах.

Для получения выгрузки следует нажать соответствующую кнопку экспорта. Выбранные данные преобразуются в файл CSV с разделителем «;» и кодировкой UTF-8, который скачивается браузером. Экспорт предусмотрен для заявок, объектов и затрат автопарка. Прецеденты отчётов доступны администратору, менеджеру и руководителю без изменения операционных данных.

## Диаграммы прецедентов

Диаграмма прецедентов для сотрудников и клиента, а также диаграммы состояний заявки, наряда и техники приведены в файле `diagrams.md` (рисунки в формате Mermaid, при необходимости экспортируются в растр для пояснительной записки).

Отдельно отображать диаграмму только для полностью неавторизованного посетителя нецелесообразно: без учётной записи доступен по существу прецедент входа (и страница отказа в доступе). Регистрация клиента «с улицы» в системе не реализована — доступ выдаёт сотрудник. Клиентский контур после выдачи учётной записи охватывает просмотр своих заявок, создание заявки и отмену новой заявки; коммерческие и ресурсные прецеденты ему недоступны.
